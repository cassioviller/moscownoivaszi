# Spec S0.1 — Retirada & Devolução (fechar a saída da jornada)

> **Fatia** do roadmap `2026-06-03-roadmap-comercial-financeiro-comissao-design.md`.
> **Aquecimento** — independente da cadeia comercial; pode ir já.
> **Tamanho:** pequeno. Sem migração de banco. Sem mudança no motor nem na jornada.

---

## 1. Problema

A jornada da noiva nunca encerra. As etapas **`retirado`** e **`devolucao`**
(`jornada.ts`) dependem de `BloqueioVestido.retiradaDataReal` e `.devolucaoDataReal`,
mas **nenhuma tela escreve esses campos** — então toda noiva fica presa em "Em provas"
para sempre, e o histórico nunca fecha.

## 2. Descoberta-chave (o que JÁ existe)

Esta fatia é pequena porque a infraestrutura já está pronta:

1. **Schema:** `retiradaDataReal` e `devolucaoDataReal` já existem em `BloqueioVestido`
   (`prisma/schema.prisma:283-284`). **Nenhuma migração.**
2. **Motor:** `calcularJanelas` (`motor.ts:48-93`) já interpreta esses campos para
   reserva:
   - retirada presente → âncora do **uso** na retirada (em vez de `casamento − usoDiasAntes`);
   - retirada sem devolução → uso **aberto** até `FUTURO_DISTANTE` (peça fora por tempo
     indeterminado, bloqueia qualquer reserva futura — `motor.ts:78-81`);
   - devolução presente → uso fecha na devolução e a **lavagem** segue dela (`motor.ts:69-77`).
3. **Jornada:** `fatosDeLead` (`leads.ts:144,146`) já deriva `temRetirada`/`temDevolucao`
   desses campos. **Nenhuma mudança em `jornada.ts`/`leads.ts`** — as etapas acendem
   sozinhas assim que os campos forem gravados.
4. **Página/ações:** o detalhe da reserva já tem o par `page.tsx` + `actions.ts` com o
   padrão de Server Action (`getSessaoComLoja` → `podeNoModulo` → data layer → redirect
   com query-param) e as fases (`fases`) já desenham o bloco de indisponibilidade.

**Conclusão:** falta só **(a)** uma função de data layer que escreve os campos com
validação, **(b)** duas Server Actions, **(c)** um card na página de detalhe.

## 3. Escopo

**Dentro:**
- Data layer para registrar/corrigir retirada e devolução de uma `RESERVA_CASAMENTO`.
- Server Actions na pasta `reservas/[bloqueioId]/actions.ts`.
- Card "Movimentação do vestido" na página de detalhe da reserva.
- Testes de unidade do data layer.

**Fora (YAGNI):**
- Mudar motor, jornada ou schema.
- Retirada/devolução para **manutenção** (já tratada por `criarManutencao`).
- Notificação/automação de devolução atrasada (vira "atenção" no dashboard, fatia futura).
- Limpar o enum morto `Lead.etapa` (fatia de higiene separada).

## 4. Regras de negócio e validação

Operações sobre **uma reserva** (`tipo = RESERVA_CASAMENTO`; `obterReservaDetalhe` já
devolve `null` para manutenção/outra loja — **falha fechada** por tenant).

Estado-alvo (patch dos dois campos), validado como um todo antes de gravar:

1. **Registrar retirada** exige `casamentoData` presente (toda reserva tem) e um **dia
   válido** (`YYYY-MM-DD`).
2. **Registrar devolução** exige **retirada já registrada** (não se devolve o que não foi
   retirado) → recusa `sem_retirada`.
3. **Devolução ≥ retirada** → senão recusa `data_invertida`.
4. **Limpar retirada** enquanto a devolução está setada é incoerente → recusa
   `devolucao_orfa` (limpe a devolução primeiro). Limpar **devolução** sozinha é
   permitido (correção de engano) e reabre o uso.
5. **Fail-closed pelo motor:** antes de gravar, **projetar** o bloqueio com os valores
   propostos via `calcularJanelas`; se lançar (ex.: retirada anterior ao início da
   preparação inverteria a janela), recusa `datas_invalidas`. Mesma filosofia do
   `reservarVestido`, que consulta o motor antes de gravar.
6. **Idempotência:** gravar o mesmo valor de novo é inócuo.

> Consequência que a UI precisa deixar clara: **retirar sem devolver deixa o vestido
> indisponível por tempo indeterminado** (o motor bloqueia toda reserva futura até a
> devolução). Não é bug — é a regra do Grill 2.

## 5. Data layer

Arquivo: `src/lib/disponibilidade/reservas.ts` (junto das demais operações de reserva).
Convenção de retorno discriminado idêntica a `ResultadoProva`.

```ts
export type ResultadoMovimentacao =
  | { ok: true }
  | { ok: false; motivo:
      | "reserva_invalida"     // não existe / outra loja / é manutenção
      | "sem_retirada"         // devolução sem retirada
      | "data_invalida"        // dia mal formado
      | "data_invertida"       // devolução < retirada
      | "devolucao_orfa"       // limpar retirada com devolução setada
      | "datas_invalidas" };   // motor recusou (janela inverteria)

/**
 * Define o estado de movimentação de UMA reserva (retirada/devolução). Patch: campo
 * ausente = não mexe; `null` = limpa; "YYYY-MM-DD" = grava. Valida o estado final
 * inteiro (regras §4) e projeta pelo motor antes de gravar. Tenant-scoped.
 */
export async function definirMovimentacaoReserva(
  lojaId: string,
  bloqueioId: string,
  patch: { retiradaDataReal?: string | null; devolucaoDataReal?: string | null },
): Promise<ResultadoMovimentacao>;
```

Implementação (esboço):
1. `tenantPrisma(...).bloqueioVestido.findUnique({ where: { id } })`; se não existe ou
   `tipo !== "RESERVA_CASAMENTO"` → `reserva_invalida`.
2. Calcular o estado final (atual + patch). Validar §4.1–§4.4 sobre strings de dia.
3. Montar um `Bloqueio` (via `toBloqueio` sobre o registro com os campos trocados) e
   chamar `calcularJanelas(...)` dentro de `try/catch` → `datas_invalidas` se lançar.
4. `update` com `meiaNoiteUTC(dia)`/`null` nos campos tocados. (Reusa `meiaNoiteUTC`,
   já no arquivo.) Carimbo de loja pelo `extendedWhereUnique` do tenant (P2025 protege
   cross-loja, como em `cancelarReserva`).

> Decisão: **um** patch em vez de quatro funções (registrar/limpar × retirada/devolução).
> A validação é interdependente (devolução depende de retirada), então validar o
> **estado final** num lugar só evita regras espalhadas.

## 6. Server Actions

Arquivo: `src/app/(app)/loja/[lojaId]/reservas/[bloqueioId]/actions.ts` (já existe).
Espelhar o helper local que as ações de prova/ajuste usam.

- `registrarRetiradaAction(formData)` → `definirMovimentacaoReserva(loja, id, { retiradaDataReal: dia })`
- `registrarDevolucaoAction(formData)` → `{ devolucaoDataReal: dia }`
- `corrigirMovimentacaoAction(formData)` → patch geral (editar/limpar datas)

Cada uma: `getSessaoComLoja()` → checar permissão → chamar data layer → `redirect` de
volta ao detalhe com `?ok=movimentacao` ou `?erro=<motivo>` (padrão da página).

**Permissão (decidido):** aceitar **`leads:editar` OU `ajustes:editar`** (o mais
inclusivo) — registrar movimentação avança a jornada, mas a costureira que entrega/
recebe a peça também precisa registrar. A action passa se **qualquer um** dos dois for
verdadeiro.

## 7. UI — card "Movimentação do vestido"

Na `page.tsx` do detalhe, **entre** o bloco de fases e o de provas. Tom Concierge
(marfim/champagne; bordô só no botão de ação principal). Estados:

- **Nada registrado:** "Vestido ainda no atelier." + form de **data de retirada**
  → botão "Registrar retirada".
- **Retirado, não devolvido:** "Retirado em DD/MM — com a noiva." Aviso delicado:
  *"Enquanto não registrar a devolução, o vestido fica indisponível para outras noivas."*
  + form de **data de devolução** → "Registrar devolução". Link discreto "corrigir/desfazer".
- **Devolvido:** "Devolvido em DD/MM." (jornada encerrada como **Devolvido**) + link
  discreto "corrigir".

Datas em `<input type="date">`. Mensagens de erro humanas mapeadas dos `motivo`.

## 8. Efeito na jornada (verificar, não implementar)

- `retiradaDataReal` setado → `temRetirada` → etapa **Vestido retirado**.
- `devolucaoDataReal` setado → `temDevolucao` → etapa **Devolução**; `estagioDaNoiva`
  marca a jornada como **encerrada "Devolvido"** (`jornada.ts:85`).
- As fases na própria página de detalhe também mudam (uso fecha, lavagem aparece),
  porque o motor já reage. Conferir visualmente.

## 9. Testes

Novo `src/lib/disponibilidade/reservas-movimentacao.test.ts` (ou estender o teste de
reservas), cobrindo `definirMovimentacaoReserva`:

1. Retirada válida grava e projeta uso aberto.
2. Devolução válida (≥ retirada) grava; uso fecha + lavagem.
3. Devolução **sem** retirada → `sem_retirada`.
4. Devolução **antes** da retirada → `data_invertida`.
5. Limpar retirada com devolução setada → `devolucao_orfa`; limpar devolução sozinha OK.
6. Dia mal formado → `data_invalida`.
7. Retirada absurdamente cedo (inverte preparação) → `datas_invalidas` (motor recusou).
8. `bloqueioId` de manutenção → `reserva_invalida`.
9. **Isolamento:** outra loja não grava (P2025 / sem efeito), espelhando os testes de
   `cancelarReserva`.

Jornada já tem cobertura de `temRetirada`/`temDevolucao`; não reescrever — só confirmar
verde.

## 11. Riscos / decisões a confirmar

- **Permissão** (`leads:editar` vs também `ajustes:editar`) — §6. Baixo risco; confirmar
  com o dono na implementação.
- **Retirada muito cedo** invertendo a preparação: tratada como `datas_invalidas` via
  motor; confirmar que a mensagem de UI orienta ("a retirada não pode ser antes do
  início da preparação").
- **Reabrir devolução** (limpar) reabre o uso e pode recolidir com uma reserva criada no
  intervalo? Não: limpar devolução volta ao estado "uso aberto" (mais restritivo, nunca
  menos), então não cria conflito novo. Anotado para o teste 5.

## 12. Definição de pronto

Uma reserva pode ter retirada e devolução registradas pela UI; a jornada da noiva
alcança **Vestido retirado** e **Devolução** (encerrando como "Devolvido"); as fases do
vestido refletem a movimentação; data layer coberto por testes; gates verdes.
