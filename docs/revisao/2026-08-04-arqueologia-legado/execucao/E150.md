# E150 — O contrato não vende peça que não reservou

## O defeito, e por que ele não aparecia em revisão

Duas listas chegam ao `POST /contratos` de **fontes independentes**:

| | De onde vem | O que significa |
|---|---|---|
| `itensSnapshot` | dos itens do orçamento (`contratos.ts:250-256`) | o que foi **vendido** |
| `bloqueioIds` | do **corpo da requisição** (`:296-303`) | o que foi **reservado** |

Nada obrigava as duas a falarem da mesma peça. E o schema declara, por escrito,
que a descrição em texto é o registro autoritativo (`contratos.ts:66-69`) —
então um item apontando `vestidoId` sem reserva correspondente fechava com
**201** e deixava a peça livre para a próxima noiva do mesmo sábado.

Não aparecia em revisão porque **pela tela não acontece**:
`pages/orcamentos/[id].tsx:638-641` já manda todas as reservas da noiva não
desmarcadas. O defeito só existe fora dela — e "fora dela" inclui qualquer
integração futura, o portal, e o próprio `curl` que a S-D4 já usava como
cenário.

**A evidência de que isso é peça, e não frase.** O caderno do ateliê numera a
peça componente como item do acervo, com ordem própria. Na semana de 13–19/07 a
mesma noiva ocupa duas linhas, e quem escreveu anotou o motivo ao lado:

```
Gabriela  1) Dayfini + [apagado]
Gabriela  5) Manga renda c/ saia lisa   (Mesma noiva Dayfini)
```

São **11 conjuntos em 14 semanas**, e o mesmo `Bolero Ricca Sposa` sai em
**duas semanas distintas, para noivas diferentes** (13–19/07, Danielle;
07–13/09, Laiza). É peça que circula.

## O tipo que faltava

`orcamento_item_tipo` era `["VESTIDO", "SERVICO", "AJUSTE"]`. Sem um tipo
próprio, o bolero virava `SERVICO` (que não tem `vestidoId`) ou `VESTIDO` com
`vestidoId` nulo — e nos dois casos **nenhuma reserva, nenhum conflito
possível**.

`ACESSORIO` entra **depois de VESTIDO**, porque é o vizinho dele em natureza —
peça física do acervo, com código e reserva próprios — e antes de `SERVICO` e
`AJUSTE`, que não são peça nenhuma:

```sql
ALTER TYPE orcamento_item_tipo ADD VALUE IF NOT EXISTS 'ACESSORIO' AFTER 'VESTIDO';
```

Molde do E49 (parcela `PARCIAL`): instrução única, sem `BEGIN`, `IF NOT EXISTS`
para ser idempotente — `ALTER TYPE ... ADD VALUE` não roda em transação que
também use o valor novo. Aplicado no banco de dev:

```
$ psql -c "select enum_range(null::orcamento_item_tipo);"
 {VESTIDO,ACESSORIO,SERVICO,AJUSTE}
```

O OpenAPI é a fonte da verdade (4 ocorrências do enum), e o codegen propagou
para `api-zod` (17 sites) e `api-client-react` (4).

## A guarda

`routes/contratos.ts` — a lista dos vestidos efetivamente reservados é colhida
na **mesma passada que já os valida**, e a checagem roda antes da transação:

```ts
const pecasVendidas = itensSnapshot.filter(
  (it) => (it.tipo === "VESTIDO" || it.tipo === "ACESSORIO") && it.vestidoId,
);
const semReserva = pecasVendidas.filter((it) => !vestidosReservados.has(it.vestidoId!));
```

Duas decisões de escopo, ambas para não trocar um defeito por um atrito:

1. **Só VESTIDO e ACESSORIO.** `SERVICO` e `AJUSTE` não são peça física e não
   têm `vestidoId`.
2. **Só quando o item JÁ aponta uma peça.** Item de descrição livre segue
   passando — exigir reserva de algo que não está no acervo travaria a venda
   por uma frase.

O erro segue a régua do E145 (código no campo do código, frase no `detalhe`), e
a frase diz o **risco**, não o nome da coluna:

```json
{
  "error": "ITEM_SEM_RESERVA",
  "detalhe": "O contrato vende uma peça que não está reservada — ela pode sair para outra noiva no mesmo fim de semana.",
  "campos": [{ "campo": "itens", "motivo": "«Bolero Ricca Sposa» não tem reserva neste contrato" }]
}
```

## O que eu errei — e por que a regra 14 se pagou duas vezes hoje

Encadeei a API e o E2E num comando só, assim:

```
cd artifacts/api-server && vitest run > api.log; pnpm run test:e2e > e2e.log
```

O `cd` do primeiro comando **persistiu**, e o E2E foi procurado no pacote da
API. O log inteiro do E2E foram quatro linhas:

```
 ERR_PNPM_NO_SCRIPT  Missing script: test:e2e
```

`E2E_EXIT=1`. **Nada rodou errado; simplesmente não rodou** — e o código de
saída era idêntico ao de uma passada com as duas falhas conhecidas de
`09-financeiro`. Se eu tivesse confiado no `EXIT=1` e concluído "são os dois
vermelhos de sempre", teria commitado um épico cujo E2E nunca executou.

É a **regra 14** cobrando pela segunda vez na mesma sessão (a primeira foi o
`tail -30` do E148), e agora por um motivo novo: ela não protege só contra
truncar a saída — protege contra **confundir ausência de resultado com
resultado conhecido**. Quando a suíte já tem vermelhos esperados, o código de
saída deixa de distinguir "falhou como sempre" de "não rodou".

**Régua para o resto da rodada:** suíte encadeada roda com caminho absoluto ou
`pnpm -w`, e o log se confere pela LINHA DE RESUMO (`N passed`), nunca pelo
código de saída.

## Visto de passagem

*(Também na tabela de Sobras — regra 12.)*

- **S-A14** — o **`vestidoId` de `contrato_itens` e `orcamento_itens` é `set
  null`** (`contratos.ts:75`, `orcamentos.ts:54`). Apagar um vestido do acervo
  transforma um item com peça num item de descrição livre — e, a partir deste
  épico, a guarda deixa de valer para aquele contrato em qualquer reedição
  futura. Não é regressão (o comportamento é o de sempre e o snapshot preserva
  a descrição), mas a régua nova depende de um vínculo que o schema deixa
  evaporar. Vale decidir se peça vendida pode ser apagada do acervo.
